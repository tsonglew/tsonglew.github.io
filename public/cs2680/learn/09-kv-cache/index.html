CHAPTER 09 / 推理与系统

KV cache 与前缀复用

算清上下文的内存账，理解缓存究竟省掉哪段计算。

进阶建议阅读 30 分钟，练习另计自编配套教程
读完这一章，你应该能
  • 推导标准 attention 的 KV cache 内存公式并区分 MHA 与 GQA
  • 解释 PagedAttention 如何改善分配与碎片问题
  • 识别可复用前缀，设计冷缓存与热缓存对照实验

为什么保留 K 和 V

在自回归 Transformer 中，新 token 的 query 需要和历史 token 的 key 比较，再用 attention 权重组合历史 value。如果每生成一个 token 都重新计算全部历史 K、V，就会反复做同一部分工作。KV cache 把每一层已处理 token 的 key 和 value 保存下来；下一步只计算新增 token 的状态，再读取历史缓存。

缓存是运行状态，不是模型权重，也不是完整答案的复用。它会随有效上下文增长，并在多请求并发时占用大量内存。通常不保存历史 query，因为未来 token 需要的是历史 K、V。这里讨论标准 Transformer attention 的逻辑容量；滑动窗口、混合状态模型、压缩注意力等结构会改变公式，不能直接照搬。

把每个维度乘出来

对批中长度相同、没有共享的 B 条序列，设层数 L、序列长度 T、KV head 数 Hkv、每个 head 维度 D、每个元素字节数 s，则 KV bytes = 2 × B × L × T × Hkv × D × s。前面的 2 分别代表 K 和 V。长度不同时，把 B×T 换成各序列长度之和；上下文长度包含已保留输入与已生成 token。

MHA 通常每个 query head 对应一个 KV head，因此 Hkv 等于 query head 数；GQA 让多个 query head 共享一组 K、V，Hkv 更少。假设 B=1、L=32、T=4096、D=128、s=2，MHA 的 Hkv=32 时逻辑 KV 为 2 GiB；GQA 的 Hkv=8 时为 0.5 GiB。这是同一组假设下的四倍差异，不代表可以无损修改任意模型的 head 配置。

逻辑容量与实际显存不同

上面的公式不包含权重、激活、临时工作区、内存分配器保留空间和元数据。多卡部署也不能总是直接除以卡数，head 分片方式和复制策略会影响每卡容量。规划时先给模型与运行时留空间，再估算可容纳的活跃 token 总数，而不是只报“支持多少并发请求”。十个短请求和十个超长请求的压力可能相差很大。

如果按每条请求的最大长度一次性预留连续空间，短请求会浪费容量，长短混合还可能产生碎片。PagedAttention 将逻辑 KV 序列映射到固定大小的物理块，允许按需分配和非连续存放。它主要改善内存管理与可共享性，并没有让每个 token 的 K、V 自动变小。最后一个未填满的块仍会产生部分浪费。

还要分清缓存容量和 attention 的临时计算。标准全量 attention 在处理长输入时涉及大量 token 对之间的关系，而 KV cache 存的是每个历史位置的向量，按本章假设随长度线性增长。采用节省 attention 中间存储的内核，并不等于不再需要历史 KV。排查内存时分别列出持久缓存和本次执行的临时空间，才能判断应该减少活跃上下文，还是更换执行方法。

相同开头，才能直接复用历史

自动前缀缓存跨请求保留可复用的 KV 状态。当模型配置和 token 前缀一致时，新请求可以跳过已经计算的前缀 prefill。实践中适合复用固定系统说明、工具定义、公共文档或稳定的对话历史；把每次变化的时间戳放在最前面，则可能让共享前缀很早中断。缓存键还需正确隔离模型、适配器及租户语义。

文字含义相近不等于 token 前缀相同。调整空格、模板或工具顺序都可能影响命中。前缀缓存主要节省 prefill，不会替你生成剩余答案，也不会消除 decode 对历史 KV 的读取。十次重复请求的热缓存结果不能代表首次访问；若内存紧张发生驱逐，之前出现过的前缀也可能不再可用。

本机实验：容量与前缀敏感性

保存为 kv_lab.py 并运行。示例用词编号模拟 token，只验证共同前缀的语义，不实现推理引擎的块哈希和缓存驱逐。

def kv_bytes(layers, tokens, kv_heads, head_dim, size=2, batch=1):
    return 2 * batch * layers * tokens * kv_heads * head_dim * size

def common_prefix(a, b):
    count = 0
    for x, y in zip(a, b):
        if x != y:
            break
        count += 1
    return count

mha = kv_bytes(32, 4096, 32, 128)
gqa = kv_bytes(32, 4096, 8, 128)
print("MHA GiB", mha / 2**30)
print("GQA GiB", gqa / 2**30)
assert mha == 4 * gqa
stable = [10, 11, 12, 13]
a = stable + [100, 101]
b = stable + [200]
print("shared tokens", common_prefix(a, b))
print("timestamp first", common_prefix([1] + a, [2] + b))
assert common_prefix(a, b) == 4
assert common_prefix([1] + a, [2] + b) == 0

结果应是 2.0 GiB、0.5 GiB、共享 4 个 token，以及动态前缀下共享 0 个 token。把长度或并发翻倍，逻辑 KV 同样翻倍。把字节数从二改为一只是在做容量估算；真正的 KV 量化还有数值误差、缩放因子和实现支持问题。

怎样证明确实省了工作

设计两组输入，一组共享长前缀，一组长度相同但开头不同。在其他配置固定时分别做冷运行、重复运行与清理缓存后的再运行，记录命中的 token 数、TTFT 和完整响应时间。若输出很长，TTFT 显著下降而总耗时只下降少量是合理结果，说明 decode 仍占主导。

常见误区包括把系统提示词移动后得到的效果全归因于缓存，忽视提示词顺序可能改变质量；把总显存不下降判定为无效，忽视引擎可能预分配缓存池；以及只报命中率，不报命中 token 数和实际省下的时间。正确对照应保持任务内容与验收标准不变。

LEARN BY DOING

做一张模型上下文容量表

  1. 运行公式实验，分别计算长度 2048、4096、8192 和并发 1、4 的逻辑 KV 容量。
  2. 选择一个实际模型配置，查清层数、KV head 数、head dimension 与缓存数据类型。
  3. 构造稳定前缀和动态前缀两组请求；没有推理设备时先完成 token 编号模拟。
  4. 写出需要额外预留的三类内存，并解释热缓存可能不命中的两种原因。

验收标准

  • 公式明确包含层数、K/V 两份、字节数，并正确区分 GiB 与十进制 GB。
  • 示例 MHA 为 2 GiB、GQA 为 0.5 GiB，翻倍长度得到翻倍容量。
  • 报告没有把权重量化误称为 KV 量化，也没有宣称前缀缓存消除 decode。

合上书，检查一下

先作答，再看解释。答错的地方，正好是值得再读一遍的地方。

1. 标准 KV cache 公式中的系数 2 表示什么？

K 和 V 是两个张量；元素占用多少字节要通过独立变量 s 计算。

2. 相同长文档反复问不同问题，前缀缓存主要减少什么？

它复用共享前缀的 KV 状态，后续新 token 仍需要执行生成计算。
